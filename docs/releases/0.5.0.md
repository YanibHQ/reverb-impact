# Reverb 0.5.0 release notes

**Status:** Published on 2026-09-03

All 19 packages are public on npm with integrity metadata and SLSA provenance. The
[GitHub release](https://github.com/YanibHQ/reverb-impact/releases/tag/v0.5.0) contains the verified
package tarballs, SHA-256 checksums, CycloneDX SBOM, and machine-readable release provenance.

Reverb 0.5.0 adds negotiated v2 impact analysis across events, shared databases, implicit HTTP,
configuration, and infrastructure while preserving the complete 0.4.0 package, schema-major 1,
storage, adapter-identity, and deterministic behavior baseline. It also introduces an optional,
provider-neutral reasoning package for bounded cited hypotheses.

## Highlights

- An explicit consumer repository allowlist is resolved against one immutable registry revision.
  The producer is always included, an empty list is producer-only, and scope never expands
  transitively.
- V2 results record exact scope, consent/authorization, per-repository/per-family coverage,
  execution budgets, deterministic evidence, limitations, and output hashes.
- Five independent adapter packages cover static event/queue, database, implicit-HTTP,
  configuration, and deployment-wiring evidence. Each has its own extraction, identity,
  partitioning, compatibility, admission, and incremental lifecycle.
- `@yanib/reverb-reasoning` can add `ai_inferred`/`needs_investigation` hypotheses from one bounded,
  authorized retrieval batch. It cannot construct, remove, reprioritize, or promote deterministic
  findings.
- Release verification now packs 19 packages, compiles packed v0.4 and v2 hosts, imports every root,
  checks the CLI version, and produces checksums, SBOM, and provenance artifacts.
- The checksum-addressed
  [release benchmark](../verification/phase-005-next-generation-release-benchmark.json) includes all
  eight adapter admission states and the optional reasoning isolation boundary without claiming
  production accuracy or latency.

## Compatibility

Existing 0.4.0 hosts can remain pinned. All documented 0.4.0 exports and schema-major 1 JSON digests
are frozen, and `AnalyzePullRequest` remains the v1 behavior path. New required vocabulary exists
only through `AnalyzePullRequestV2` and separately named v2 schemas. Existing TypeScript, OpenAPI,
and Protobuf adapter IDs and identity versions do not change.

All Reverb packages must use exact version 0.5.0 together. Mixing 0.4 and 0.5 packages is unsupported.
Internal package dependencies in the release are fixed to 0.5.0.

## New public packages

- `@yanib/reverb-adapter-events`
- `@yanib/reverb-adapter-database`
- `@yanib/reverb-adapter-http`
- `@yanib/reverb-adapter-config`
- `@yanib/reverb-adapter-infrastructure`
- `@yanib/reverb-reasoning`

The CLI and reference hosts do not automatically enable the new adapters or a model provider. A host
must explicitly compose the desired packages, supply adapter configuration, select repositories,
and pass their deterministic evidence into the v2 application path.

## Storage migrations

| Store      | 0.4 level | 0.5 level | Additive data                                                 |
| ---------- | --------: | --------: | ------------------------------------------------------------- |
| SQLite     |         7 |         8 | v2 scopes, selections, analysis results, and reasoning runs   |
| PostgreSQL |         3 |         4 | workspace-isolated/RLS v2 scopes, results, and reasoning runs |

Migrations are forward-only and do not rewrite or reinterpret v1 rows. Take a transactionally
consistent backup before upgrading. The PostgreSQL logical `backupWorkspace()` drill export covers
canonical records/pointers only; deployments retaining v2/reasoning history need physical database
backup coverage with the declared reasoning-retention expiry.

## Indexing and calibration

- Existing 0.4 TypeScript, OpenAPI, and Protobuf generations remain valid for those adapters.
- Each newly enabled events, database, implicit-HTTP, configuration, or infrastructure adapter needs
  an initial bounded index. Enabling one family does not require enabling or rebuilding another.
- All new evidence strata are `UNMEASURED` and preview-only. No new family or reasoning hypothesis is
  authorized for blocking checks or automatic writes without separate representative evaluation and
  promotion.

## Optional reasoning safety

No model SDK, transport, credential, or live provider is included. Hosts must supply model-export
consent per repository, region/retention policy, exact-handle retrieval, provider transport,
cancellation, deletion propagation, and backup expiry. The core stores consent hashes, model/policy
versions, budgets, input/output hashes, and exact citation metadata—not source excerpts, prompts, raw
responses, credentials, or secret values. Disabled, missing, denied, timed-out, refused, malformed,
or failed reasoning leaves deterministic findings unchanged.

## Known limitations

- Event analysis supports declared manifests and bounded literal Kafka, SQS/SNS, and Pub/Sub forms;
  dynamic destinations remain unresolved.
- Database analysis targets bounded PostgreSQL DDL/migrations, literal SQL, and configured Prisma
  forms; other dialects, dynamic SQL, and stored procedures are partial.
- Implicit HTTP supports bounded Express, Fastify, Hono, fetch, Axios, and configured literal aliases;
  arbitrary URL construction, mounted prefixes, proxies, and runtime route registration are partial.
- Configuration analysis uses value-free declarations and literal reads; values are excluded, secret
  identities require a host salt, and computed keys remain unresolved.
- Infrastructure analysis is static and bounded. It does not execute Helm/Terraform, load provider
  state/plugins, or contact clusters/cloud APIs.
- Reasoning is hypothesis-only, requires exact two-sided citations, and has no bundled provider.
- Scope is explicit and non-transitive; organization membership is never treated as dependency
  evidence.

## Rollback

Disable external writes first, then disable reasoning and each new adapter independently. Stop v2
workers and restore the pre-upgrade database/object backup before running 0.4 binaries; do not assume
an older binary accepts a database already advanced to migration 8/4. Existing 0.4 packages can stay
pinned throughout a staged rollout. Deterministic v1 data is not deleted by the new migrations.

## Operator-gated deployment actions

Publishing this release did not deploy a runtime, apply production migrations, change GitHub App
permissions, enable a model, or modify Yanib. Those remain separate operator-approved integration
actions. Follow the [0.5.0 host upgrade guide](../operations/upgrade-0.5.0.md) before enabling Reverb
in a hosted product.
